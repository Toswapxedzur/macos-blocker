## Network-layer gap (explicit answer)
**Yes — the provider infra has no reusable HTTP/network layer.** Core (`ProviderProtocols`, `RawWebSearchProtocol`, `ProviderTestProtocol`, `ProviderModelCatalogProtocol`) is pure request-build/parse with zero networking. The only real client is `VaultClassifierApp.performProviderRequest` + `apply(credential:)` (L863/L880) — **private `@MainActor` members using `URLSession.shared`**, reachable only from the web-bridge controller for tests/catalog probes. So the executor needs **three new Core pieces**: (1) a minimal HTTP client, (2) a public arbitrary-query web-search executor, (3) a general `generateText` build+parse. No streaming/retry needed for v1; a small concurrency cap + RPM limiter suffices.

## P3.3 The research TRIGGER (concrete + justified)
**Primary trigger — low renormalized-confidence or decline, read at classify time.** In `classifyVideo`, enqueue a `ResearchTask` when, for any type's fresh `VideoClassification`: `tags.isEmpty && source == .model` (the grammar `"none"` decline, VaultLocalLLMEngine L153-157), **or** `tags.map(\.confidence).max() ?? 0 <= ResearchSettings.confidenceTrigger`.

**Justification:** `unknownTerms` — the *declared* input — is always `[]` because the engine's final name-only contract never emits it (L78/156/159), and making it emit them means a second decode pass or widening the grammar inside the KV-cache-sensitive single-name loop (the most fragile, latency-critical code, guarded by the `prompt-exceeds-context` check and the static-prefix cache invariant). The renormalized-softmax confidence (`probability(of:among:)` L219 → `confidence(fromProbability:)` L190) is already calibrated and **free** — it is exactly "the model is guessing / has no grounded basis," which is the research signal. Confidence is present on the stored `VideoClassification.tags` but dropped by `videoTagsProjection` (L390) and all `Native*` DTOs, so the detector must read it **inside `classifyVideo`** (or via `catalog.videoClassification(...)`), never the projection.

**Subject extraction happens OFF the hot path** in `GroundedResearchExecutor.resolve(task)`: a deterministic salient-entity extractor over the title (quoted phrases, hashtags, capitalized multi-word runs), capped at `maxSubjectsPerVideo`. This never touches `VaultLocalLLMEngine`.

**Weak-title creator bootstrap (§7.6, unified — option A):** when the low-confidence/decline trigger fires **and** `catalog.creatorHistogram(...)` is `nil`/empty (all seen videos weak), enqueue an additional subject `ResearchSubject(kind: .creator, subject: creatorID)`. It is keyed `creator:<creatorID>` so `matchedKnowledge`'s creator-key lookup (LocalLLMModel L456-459) injects it into that creator's future videos. No separate creator trigger — folded into the one path, exactly as §7.6 resolves.

**Dedup + rate-limit:** skip any subject whose `KnowledgeEntry.key` already exists in `catalog.knowledgeEntries` (first-sight only) and record attempted keys (incl. failures, with cooldown) in the queue's ledger; enforce `requestsPerMinute` via the token bucket + a 1–2 concurrency cap.

## P3.6 Risks to the live pill pipeline + avoidance
1. **Contention with the llama actor.** Search/generation are remote (URLSession) — no contention. The re-classify step uses the local engine; run it via direct `classifyVideo` after the original, keyed distinctly, to avoid the `inFlight` drop and races (P3.4).
2. **Push contract drift.** Never change `"video-tags-updated"` or `NativeVideoTagsBroadcast`/`NativeVideoTag`; the hub whitelist (L253) silently drops anything else. Reuse `broadcastResolvedVideoTags`.
3. **`matchedKnowledge` hot-path cost.** It's a linear scan of all entries (up to 20k) per video per type (LocalLLMModel L454-463), and substring term matching can false-positive and inflate the dynamic suffix (more decode tokens → latency, and the final contract is latency-sensitive). Mitigation: cap matched terms injected per video; keep the map small early; index later.
4. **House-rules distillation invalidates the cached static prefix** (KV cache) → uncached prefill (~300ms vs ~75-90ms). Mitigation: distillation is periodic/batched/debounced (after K corrections or T minutes, idle), **never** per-correction; append a delimited "Learned preferences" block, don't rewrite the manual string.
5. **Stale cached pills.** `cachedVideoTags` ignores `modelVersion`, so a video whose knowledge just landed keeps its pre-research row until re-classified. The trigger's re-classify of affected videos is what refreshes them; videos not re-run stay stale until their next request (known doc gap, no stale-recompute pass yet — call out as follow-up).
6. **Do NOT remove `LLMWebSearchMode.off` in this deliverable.** It's the current default and appears in init/validation/JSON (WorkspaceAssets L450/519/600); deleting it is a breaking Codable migration unrelated to adding the loop. Defer.
7. **Provider profile churn.** `reconcileClassifierTypes` (L2039) drops profiles failing `validate()`; the research provider lives in global `ResearchSettings`, so reconcile won't wipe it — but validate the referenced profile IDs at use time and skip research (don't crash) if gone.
8. **`enabled: false` default** means Phase 3 is inert until switched on — the pill pipeline is byte-for-byte unchanged when off.

## CRITICAL (breaks the build, persistence, or the live pipeline)

**C1 — `ResearchSettings` will silently never persist (or fail to build).**
`ClassifierSettings` has a **hand-written `init(from:)` (Contracts L277) + an explicit `CodingKeys` enum (L266)** and a synthesized `encode`. The plan says only "add `ResearchSettings`… (L252, `decodeIfPresent` for back-compat)" — but for this struct that is insufficient. You must edit **all three**: (a) memberwise init (or the `self.init(...)` call at L282 breaks compilation), (b) add `case research` to `CodingKeys` L266 (or synthesized `encode` never writes it), (c) add `research = try container.decodeIfPresent(...) ?? ResearchSettings()` inside `init(from:)` (or it's never read back). The naive "add a property + decodeIfPresent" compiles and runs but silently drops the entire feature's config on every load. The plan handled this meticulously for `ClassifierTypeAsset` (L828/834/873) and then under-specified the analogous, more dangerous case for `ClassifierSettings`.

**C2 — `recordResearchKnowledge` NSLock/await deadlock-or-UB.**
`LocalClassifierCoordinator` uses a **non-reentrant `NSLock`** (LocalStore L166) and `classifyVideo` takes it in two separate `withLock` blocks (L336, L366). The plan describes `recordResearchKnowledge` as "under lock: upsert + save … then for each affected … `await classifyVideo`". Two hazards: (1) if the `await classifyVideo` is inside the lock scope, you re-enter the same non-reentrant lock → **deadlock**; (2) holding an `NSLock` across an `await` means unlock can occur on a different thread than lock → **undefined behavior**. The spec must state explicitly: upsert+save under `lock.withLock {}`, **release**, then `await classifyVideo` outside any held lock.

**C3 — Inline `await queue.enqueue(...)` inside `classifyVideo` can stall the LIVE pill path.**
The plan enqueues research from inside `classifyVideo` (called on the `@MainActor` `queueVideoClassification` task, L312-320). If `enqueue` is actor-isolated and does anything more than an O(1) append — or if it's ever awaited against the rate-limited/concurrency-capped drain — research backpressure applies to the live classification await, delaying pills. Requirement to fold in: enqueue must be **fire-and-forget and non-blocking** (`Task.detached { await queue.enqueue(...) }` with a **bounded, drop-on-full** queue), never inline backpressure on the classify path.

**C4 — The `saveClassifierTypeLocalModel` dispatch reuses *throwing* parsers and breaks on the common form states.**
The plan says reuse "the existing `confidenceBand2..5` parse block and `webBool`/`positiveInteger`/`webString`". That block (App L2526-2532) **throws** if any confidence field isn't a valid `0<v<1`, and `positiveInteger` (L2024) throws on empty. For a per-type override form, when override is **disabled** (fields hidden/empty) or **partially filled**, the generic dispatch still `collect()`s the fields and the reused parser throws → the save (and the disable action) fails at runtime. This contradicts the plan's own "`LocalModelOverrides.init` clamps/drops" model. The dispatch must parse **leniently** (collect raw optionals, pass to `LocalModelOverrides.init` which clamps/drops), gated on `overrideEnabled`, not reuse the throwing global block verbatim.

## CORRECTNESS gaps

**G1 — Per-type `maximumTags` is inert on the real engine.**
`VaultLocalLLMEngine` decodes a **single grammar-constrained name** (`root ::= "a" | "b" | …`) and returns exactly one `LLMTagScore` (L159). It never emits more than one tag. So `maximumTags > 1` changes nothing in production; the pipeline's dedup/`prefix(maximumTags)` (L69-80) is effectively dead code for the shipping engine, and the plan's coordinator test only "works" because it uses `StubOnDeviceLLM` (which emits many). Deliverable B's headline per-type `maximumTags` knob is **cosmetic for the real model** — the genuinely-effective per-type knobs are `houseRules`, `allowDecline`, `confidenceThresholds`. The plan should either say so plainly or scope multi-tag decode (out of band).

**G2 — B × P3 coupling makes the confidence trigger unstable.**
The global `ResearchSettings.confidenceTrigger` (1-5) is read against `ScoredTag.confidence`, but confidence bucketing is now **per-type** (Deliverable B's `confidenceThresholds`). A user who tightens one type's thresholds shifts its whole confidence distribution downward → that type's videos routinely fall `≤ confidenceTrigger` → runaway enqueue → RPM/token budget blown. A single global trigger level cannot mean the same thing across types with different threshold vectors. The two deliverables interact and the plan treats them as independent.

**G3 — Dedup/cooldown ledger isn't persisted → failed subjects re-researched every launch.**
The queue's ledger is an in-memory `Set<String>` (actor state). Successful entries dedup correctly because they land in `catalog.knowledgeEntries` (persisted, checked via `KnowledgeEntry.key`). But **failures + cooldowns live only in memory** — on app restart the ledger is empty, so any subject that persistently yields no results (or errors) is retried on every launch, burning third-party API quota indefinitely. Persist a negative-cache (key → lastAttempt/cooldown) in the catalog, or you have an unbounded retry hole.

**G4 — `dailyTokenLimit` is declared but never enforced.**
`ResearchSettings.dailyTokenLimit = 10_000` appears in the struct and nowhere in the control flow. There is no persisted daily counter, no reset boundary, and no wiring to the existing `tokenUsage` store (App L921). As specified it's a dead field; the RPM bucket alone doesn't bound spend.

**G5 — Re-classify fan-out contends with the local llama actor, and "affected" is undefined.**
The plan's contention argument ("search/generation are remote → no contention") ignores that `recordResearchKnowledge` re-runs **`classifyVideo` locally** for each affected video. `recordResearchKnowledge(affected:)` never defines who computes `affected`. A `.creator` knowledge entry matches *all* of that creator's videos (`matchedKnowledge` creator-key lookup, LocalLLMModel L456-459); if "affected" is broad, a single research completion triggers a burst of local inference on the serialized engine actor, directly competing with live pill classification. Needs an explicit, bounded `affected` set (e.g., only the triggering entry, plus a capped/debounced backfill) and priority behind live requests.

**G6 — Non-`Sendable` coordinator captured across the queue actor / writer closure.**
`LocalClassifierCoordinator` is a plain `public final class` (LocalStore L164) with **no `Sendable`/`@unchecked Sendable`**. The plan has an `actor GroundedResearchQueue` and a writer closure calling `coordinator.recordResearchKnowledge`, plus a mutable `onVideoReclassified` closure property read/written without the lock. Under Swift 5.9 non-strict mode (Package.swift `swift-tools-version: 5.9`, no `StrictConcurrency`) this compiles with at most warnings, so it won't break the build — but it's a latent data race and will hard-fail under any future Swift 6 / strict-concurrency move. Mark the coordinator `@unchecked Sendable` (its state is lock-guarded, like `LocalStateFile` L83) and guard `onVideoReclassified`, or route the callback through the MainActor.

**G7 — `generateText` provider/format gating unspecified.**
`ProviderGenerationProtocol.prepareGenerateText` must reject `embeddingInput` (L237), `serperSearch`/`youSearch`, and validate that `ResearchSettings.llmProviderProfileID` points to a chat-capable profile (`supportsLLMConfiguration`). None of this is specified; as written it can build a nonsense body for an embedding/search profile. Also note the public `ProviderTestProtocol.parseResponse(_:format:operation:)` (L66) **already** returns `content + usage` — the plan's insistence on exposing the private `extractText`/`usage` (L270/L105) is unnecessary; reuse `parseResponse` and avoid widening API surface.

**G8 — Dangling `ResearchSettings` provider refs after deletion.**
The provider-deletion handler nulls per-type `llmAssistConfiguration`/`selectedLLMProviderProfileID` (App L1013-1020) but knows nothing about the new global `ResearchSettings.{llmProviderProfileID, webSearchProviderProfileID}`. `reconcileClassifierTypes` won't touch global settings either. Deleting a provider leaves dangling research refs. The plan's "validate at use, skip research if gone" is acceptable as a floor, but the deletion path should also null them, and this must be stated.

## MISSING (requirements not covered)

**M1 — Privacy invariant violated with no mitigation.**
`RawWebSearchProtocol` is documented as: it builds only the fixed health query and **"never incorporates collected content"** (L15-16). Phase 3 deliberately sends **subjects extracted from collected video titles and raw `creatorID`s** to third-party search + LLM providers. For an on-device, privacy-positioned classifier this is a material change: collected content and creator identifiers leave the device. The plan has no consent gate, no disclosure, no redaction/minimization, and reuses a protocol whose contract explicitly forbids this. At minimum: explicit opt-in copy naming the data flow, and subject sanitization. This is the most serious omission.

**M2 — No backfill/sweep → feature does almost nothing on an existing library.**
The trigger only fires on **new** `classifyVideo` runs. The cache-hit path (`cachedVideoTags`, L316-326) returns **before** `classifyVideo`, so already-classified low-confidence videos never enqueue research. The plan flags stale pills (risk #5) as a "follow-up," but the practical effect is that on any populated install the loop is inert until videos happen to be re-requested. A bounded backfill scan over persisted low-confidence `videoClassifications` is a core requirement, not a follow-up.

**M3 — User corrections are the strongest signal and go unused for research.**
`submitCorrection` feeds only distillation. A user correction is ground truth that the model was wrong on a *specific* video — a far higher-precision "needs grounding" signal than renormalized confidence. It should also enqueue research on that video's entities. Currently wasted.

**M4 — No ordering/idempotency mechanism for the re-classify vs live races beyond "runs later."**
"Order the research re-run after the original completes" has no enforcing mechanism; it happens to hold only because network latency exceeds the original classify. Double-broadcast for the same entry (research path + a concurrent live `queueVideoClassification`) is possible. Harmless but should be stated as intentionally idempotent.

## The trigger is weak — proposed replacement

**Why "low confidence OR decline" is the wrong signal.** Renormalized confidence (`probability(of:among:)`, engine L219) measures how torn the model is **among existing taxonomy tags for the first token** — i.e., *which* legal tag, not *whether it lacks grounding about an entity*. The research intervention (inject a `KnowledgeEntry` defining some extracted entity) doesn't resolve tag-vs-tag ambiguity, so the signal is mismatched to the fix. Worse, the trigger is **decoupled** from *what* is unknown: it fires, then a crude deterministic regex (quoted phrases / hashtags / capitalized runs over the title) guesses entities the model may already understand, while missing genuinely-unknown terms that live in the summary/text. And per G2 it's unstable under Deliverable B's per-type thresholds. Confidence being "free" (the plan's justification) doesn't make it the *right* signal.

**Better design — high-precision, model-sourced, budget-safe:**

1. **Primary = decline only.** Enqueue when the model actually declines: `source == .model && tags.isEmpty` (the grammar "none" path, L153-157). This is the unambiguous "nothing applied" signal — rare, high-precision, cheap. Drop the low-confidence branch (or gate it behind a much higher bar than default `2`).

2. **Model-chosen subject via a gated second decode** — this is the real fix to "`unknownTerms` is always `[]`". Instead of widening the fragile single-name grammar on the hot path, run **one extra tiny constrained decode only on the rare decline case**: a grammar that emits a single salient noun-phrase drawn from title/summary (or "none"). Common-path latency is untouched (it never declines), and you get a **model-selected** research subject far better than a title regex — producing exactly the `unknownTerms` the architecture was designed around. This directly refutes the plan's stated reason for abandoning `unknownTerms` (you don't touch the common single-name loop at all).

3. **User correction = research trigger** (M3). Highest-precision "the model lacked grounding here" signal; enqueue entities from any corrected video.

4. **Weak-creator bootstrap** — keep the plan's folded-in creator subject when the trigger fires and `creatorHistogram(...)` is nil/empty (keyed `creator:<creatorID>`), which is a good idea already.

5. **Budget discipline** — because decline + corrections are rare, RPM/daily-token limits are rarely hit; the negative-cache (G3) plus persisted daily counter (G4) keep it bounded across restarts.

Net: replace "low-confidence OR decline + title-regex extraction" with "decline (+ gated second-decode subject) OR user-correction," decoupled from per-type thresholds, with persisted dedup/cooldown and enforced daily budget.
